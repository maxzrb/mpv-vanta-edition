# 色彩管线软件闭环验证（2026-10-11）

本轮按用户要求验证软件数值、实际资源格式和提交给系统的色彩空间，不以校色仪或 HDR 实体屏幕为完成条件。

**后续修复记录：** 下述内容保留修复前的审计状态。随后已通过默认单线程范围转换修复全范围 10／12bit 中点偏差，并完成实际 GPU、全码阶、HDR／ICC、硬解和滤镜交接验证；见[配置修复报告](全范围色度中点配置修复-20261011.md)。核心二进制本身未改；默认 perceptual／自适应 HDR→SDR 的完整独立参考仍待补齐，因此历史总验收 FAIL 不改写为全面通过。

**软件总验收：不通过。** 实测确认色彩管理的主要数学路径成立，也发现了配置中的多余映射和当前核心的全范围色度中点错误。已经修正前者；后者仍然存在，不能把当前实现签为“所有片源颜色准确”。默认 perceptual 色域映射及自适应 HDR→SDR 的完整独立算法参考也仍待补齐。失败证据已经足以否定当前实现全面正确的结论，无需等待硬件测量。

“mpv 管线精度不高”需要拆成可测量的事实：**本机当前 gpu-next 的被测 Shader 使用 FP32 运算，主图像中间写回及 scRGB 交换链使用 FP16 存储，源整数上传保持原码值。它有浮点量化，不能称为整链整数无损。** 两种 API 得到相同错误，也不能证明运算正确。

## 1. 验证对象和方法

本机 i5-12600KF、RX6600、32 GiB，mpv `36bf3d529059a947d6700adefeab3b421e537c19`，内置 FFmpeg `5d4755f7d`，libplacebo `0d043c7f6f79cd3687c023454bdacbe615e4d96f`。没有重编译、替换核心，也没有继续增加解码线程。

诊断进程采用活动配置的色彩／画质脚本，排除 UI、历史记录、徽标等旁路任务。所有 GPU 主链读回测试固定 `hwdec=no`。测试用显示场景从色彩管理器现有的 `user-data/display-info`、`user-data/display-color` 入口注入，使 SDR ACM、经典 SDR、ICC、HDR 数学场景可重复；不把诊断窗口所在屏幕的能力当作测试输入。

闭环逐段检查如下：

1. FFV1 测试源的已知整数码值，或独立 FFmpeg 解码的真实 AV1 平面。
2. 实际绑定给 GPU 的 R8／R16 整数纹理：逐字节比较全部可见源像素。
3. 每次主图像绘制／计算后的实际纹理写回：读取格式和原始像素。
4. 最终 Present 前的交换链像素：与最后一次写回、独立数值参考比较。
5. 实际提交的色彩空间：D3D11 的成功 `SetColorSpace1` 和 Vulkan 的交换链 `colorSpace`。
6. 实际编译 Shader：D3D11 HLSL／DXBC，Vulkan SPIR-V 浮点类型及精度装饰。

数学参考使用独立 Python 浮点公式计算 YUV 范围归一化、601／709／2020 NCL 矩阵、sRGB／BT.1886／PQ／HLG 传递函数及 2020→709 原色矩阵。判断不是仅比较两个后端，也不是只看截图或配置宣称。

读回会同步／暂停 GPU，因此**不用于性能测量**。另以原有交换链读回器做对照，两种 API 的全部 65,536 个 RGBA 输出像素均逐字节一致，验证主链插桩在该对照场景中没有改变图像。

## 2. 实际精度及交接格式

| 环节 | 实际观测 | 验证结果 |
|---|---|---|
| YUV 8bit 源 | R8 UNORM | 原码值逐字节一致 |
| YUV 10／12／16bit 源 | R16 UNORM，低位存储再由 Shader 归一化 | 原码值逐字节一致 |
| RGB16 PNG 上传／重排 | RGBA16 UNORM | 全部 65,536 个灰阶码值和所测 RGB 色块不丢码 |
| GPU 运算 | D3D11 实际 DXBC 浮点指令；Vulkan `OpTypeFloat 32`，无 `RelaxedPrecision` | 被测 Shader 使用 FP32 算术 |
| 主图像中间写回 | D3D11 `DXGI_FORMAT_R16G16B16A16_FLOAT`；Vulkan `VK_FORMAT_R16G16B16A16_SFLOAT` | FP16 存储，存在量化 |
| SDR ACM／D3D11 HDR scRGB | RGBA16F，线性 709 | D3D11 色彩空间 1；Vulkan SDR 色彩空间 1000104002，均与像素编码匹配 |
| 经典 SDR／显式 ICC | RGB10A2，sRGB 编码，保留抖动 | 色彩空间 0；原始读回为 10bit 交换链 |

这里的 FP32 是 Shader 算术类型，不表示所有中间缓冲都是 FP32，也不保证驱动每个超越函数具有 float64 精度。主图像逐段资源格式已实测，不再用“自动选择”推断实际精度。

libplacebo 固定源码中优先选择 16bit 浮点中间格式，与实际捕获相符：[renderer.c](https://github.com/haasn/libplacebo/blob/0d043c7f6f79cd3687c023454bdacbe615e4d96f/src/renderer.c)。scRGB 采用线性 BT.709 原色表达广色域，并允许负值和大于 1 的值；本轮没有在该交接点把它们截成普通 SDR。

Windows 官方高级色彩交接也采用 FP16／scRGB，其原色为 BT.709、传递为线性，并允许扩展数值范围。因此采用这条交接路线符合系统的软件契约；不能因中间存储是 FP16 就认定色彩管理路线错误。[Microsoft 高级色彩文档](https://learn.microsoft.com/en-us/windows/win32/direct3darticles/high-dynamic-range)

## 3. 矩阵、范围和位深的独立验收

测试包含 8／10／12／16bit × 601／709／2020 NCL × 有限／全范围 × D3D11／Vulkan，共 **48 组**。每组 16 个色块，源三个平面整帧比较、首个写回色块内逐像素一致性检查、之后的同尺寸写回至交换链全部 RGB 像素逐字节检查。

| 项目 | 结果 |
|---|---|
| GPU 源整数上传 | 48／48 组全部原码值一致 |
| 同尺寸复制／呈现 | 48／48 组所有 RGB 像素保持一致 |
| 对独立色彩公式的线性误差 | 42 组满足 `<0.00125`；6 组失败 |
| 失败组 | 全范围 10bit 的 601／709／2020，两个 API 均失败 |

线性误差阈值用于本轮浮点管线的数值回归，不等同于全部颜色的 ΔE 证明；失败组还具有独立的中性灰偏色反例和 GPU 常量证据，不是仅凭阈值给错误命名。

| 全范围 10bit 矩阵 | 两种 API 的最大线性误差 | 中性灰最大通道差 |
|---|---:|---:|
| 601 | 0.001558063 | 0.002929688 |
| 709 | 0.001907037 | 0.002929688 |
| 2020 NCL | 0.002883600 | 0.004394531 |

### 3.1 全范围色度中点错误的原因

读取实际 D3D11 色彩解码常量，反算蓝色通道的偏置／Cb 系数得到中点：

| 信号位深 | 正确中点 | GPU 实际中点 |
|---|---:|---:|
| 8 | 128/255 = 0.501960784 | 0.501960782 |
| 10 | 512/1023 = 0.500488759 | **0.500007645** |
| 12 | 2048/4095 = 0.500122100 | **0.500007645** |
| 16 | 32768/65535 = 0.500007630 | 0.500007645 |

10／12bit 的 GPU 解码矩阵使用了 16bit 存储对应的中点。独立错误模型能在最大约 0.000482 的 FP16 写回误差内重现实际输出，且 8／16bit 对照的中点正确。

对应固定源码路径是：renderer 采样归一化后更新 `repr.bits`，随后色彩解码拿到已归一化的 16bit 表示；全范围码值的比例与中点因此不再匹配。有限范围采用位移定义，所测用例不触发同类偏差。上游直接解码中的位深中点修正见 [d9922613](https://github.com/haasn/libplacebo/commit/d9922613bfe26c974a7e7890fdebcda61be023d8)，但本机 renderer 路径的实测仍有此问题，不能据存在该提交就认定已经修复。

**12bit 全范围也有错误，只是本组色块的误差尚未越过统一阈值。** “12bit 数值测试通过”不能盖过中点错误的直接证据。

### 3.2 不重编译的候选处理

诊断配置加单线程 `lavfi`／`zscale`，将全范围 10／12bit 转为有限范围 16bit 后交给原渲染器。12 组（两种位深 × 三种矩阵 × 两种 API）均通过；所测色块的转换后整数能逆算回原整数，最大线性误差分别约 0.000395／0.000461。

随后补测了全部码阶：10bit 的 1,024 个、12bit 的 4,096 个码值，在三个平面分别穷举；两种 API 的转换后整数均可逆算回原码值，未发生码阶合并。这里验证的是范围转换前后整数的可恢复性，不表示最终 FP16 缓冲也无损。中性灰全码阶最大线性误差约 0.000488／0.000500；12bit 最终有 4,001 个不同值，仍有 FP16 写回量化。全范围 10／12bit、709／2020 原色、PQ／HLG 共八组 D3D11 HDR 数值参考也通过。

独立 FFmpeg 的 4K 原始帧至 null 测试固定解码／编码线程 1、滤镜线程 1，96 帧、ABBA 各两轮，对比候选范围转换与无转换基线：

| 信号位深 | 每帧总耗时增加 | 每帧进程 CPU 用时增加 |
|---|---:|---:|
| 10 | 1.19271 ms | 7.00000 ms |
| 12 | 0.76042 ms | 7.81771 ms |

总耗时包含原始帧读取和处理调度，CPU 用时为 user＋system 累计；两者含义不同，不能把它们说成精确的 mpv 单滤镜耗时，更不能换算为完整播放帧率。初轮与 GPU 测试重叠的时序数据已舍弃，表内为后续无并行 GPU 诊断的完整重测。

候选证明不重编译可以处理该偏差，但额外 CPU 工作不适合宣传为无成本优化。**没有启用到生产配置。** 硬解交接、已有滤镜链相互作用及真实 mpv 播放代价仍须验证；目前默认链的核心中点缺陷仍然存在。

## 4. 已修正的重复色域映射

活动 `color-target.lua` 原先仅对 BT.2020／P3 scRGB 交接显式保留源色域，遗漏 BT.709。该遗漏使 709→scRGB 路径保留了不必要的 perceptual 3D LUT 运算。在已经采用标准 scRGB 交给 Windows 终端管理的场景，播放器应该保留源色域，不再叠加此映射。

本轮在 SDR ACM 和 HDR scRGB 两处补入 BT.709。目标原色仍为 BT.709、目标传递仍为 scRGB；保留原 HQ、线性缩小、位深与浮点输出，未通过降低质量换速度。D3D11 和 Vulkan 的 SDR ACM 都应用同一修正。

同轮修正前后，对全部 65,536 个 RGB16 灰阶逐个计算 sRGB EOTF 参考：

| 项目 | 修正前 D3D11 | 修正前 Vulkan | 修正后两种 API |
|---|---:|---:|---:|
| 最大线性误差 | 0.001599507 | 0.001580086 | **0.000488305** |
| 最大灰阶 ΔL* | 0.06667048 | 0.06667048 | **0.02955101** |
| 输出不同线性值数量 | 9,387 | 9,387 | **10,870** |
| D3D11 色彩 Shader 的 3D LUT／指令槽 | 有／80 | — | 无／13 |

ΔL* 仅针对中性灰亮度，不能冒充 RGB 全色域 ΔE。输出不同值数量也不是均匀量化位深。

### 4.1 性能对照

独立的无插桩 mpv 进程，以修正前／后／后／前（ABBA）顺序，每轮预热 5 秒，读取 `vo-passes` 的 GPU 样本中位数，再取相同状态两轮的均值。AV1 固定 32 解码线程，HEVC 固定 16 解码线程；前后设置一致。

| 片源／API | GPU 色彩末段修正前 | 修正后 | 耗时下降 |
|---|---:|---:|---:|
| OP AV1／D3D11 | 0.33165 ms | 0.29780 ms | 10.21% |
| OP AV1／Vulkan | 0.33673 ms | 0.30174 ms | 10.39% |
| 独立 HEVC10／D3D11 | 0.64212 ms | 0.61991 ms | 3.46% |
| 独立 HEVC10／Vulkan | 0.19128 ms | 0.17178 ms | 10.19% |

这些是 1024×576 窗口下的 GPU 分段耗时，`color encoding` 段可能合并横向缩放。不能换算为播放器总体提升 10%，也没有据此宣布 OP 整片零丢帧。结果证明此次去除冗余处理的收益跨片源、跨 API 存在；样本规模仍为每种组合两轮前／两轮后。

## 5. 灰阶、广色域、HDR 和缩放

独立公式验证结果如下。无缩放色块的中间写回到交换链保持相同 RGB 值，读回验证负值和 HDR 高于 1 的值没有在 scRGB 交接前被截断。

| 测试 | API | 最大误差／结果 |
|---|---|---|
| 2020→709 广色域 SDR | 两种 | 线性误差 0.000488281；保留负分量 |
| 1024 个灰阶 | 两种 | 全部 1024 个不同输出值；最大线性误差 0.000488281 |
| RGB16 彩色色块 | 两种 | 整数上传一致；线性误差 0.000318012 |
| 12bit 有限范围全合法灰阶 | 两种 | 3,505 个源码阶 → 3,498 个输出值；最大线性误差 0.000488281 |
| 黑白交替纹理线性缩小 | 两种 | 参考 0.5，最大误差 0.000244141 |
| PQ／BT.2020→scRGB | D3D11 | 最大 scRGB 误差 0.0625（80 nit 单位下为 5 nit）；含 10,000 nit 白和负值 |
| HLG／BT.2020→scRGB | D3D11 | 最大 scRGB 误差 0.007812866；1000 nit、黑位 0 的受控场景 |
| PQ／BT.709→scRGB | D3D11 | 最大 scRGB 误差 0.022902371 |

HDR 数值验收采用绝对加相对误差预算 `0.00125 + 0.002×abs(reference)`，独立验证 PQ 的绝对亮度和 HLG 的峰值相关 OOTF。软件场景令目标峰值覆盖源峰值，验证传递／原色转换而不压缩亮度；因此这些结果不等于默认自适应 HDR→SDR 映射算法的全面验证。当前管理器真实 HDR 路线仍只支持 D3D11，本轮没有把 Vulkan 的 SDR 数学验证说成 Vulkan HDR 管理器验收。

全灰阶测试明确表明 FP16 存储会合并某些码阶。保留高位深源和 FP32 算术，能降低误差，但不能消除 FP16 写回量化；不能宣称 12bit 片源每个灰阶在最终线性缓冲中都不同。

## 6. 经典 SDR 与显式 ICC

经典 SDR 的真实 RGB10A2 交换链保留原抖动。8bit 全范围 601、12bit 有限范围 709 两种 API 的色块平均编码误差分别约 0.001029／0.001200。单像素误差预算包含 FP16 写回、原配置抖动和 RGB10 最终量化，不能直接用“截图某像素不相等”判断颜色转换失败。

广色域 2020→709 的纯矩阵参考与当前默认 perceptual 映射平均差约 0.002078。**该比较不能把默认算法判为错误**：perceptual 本来可能改变颜色，完整算法参考尚未建立；记录为参考差异，未算作全色域通过。

ICC 验证另外构造已知精确 Gamma=2 的诊断目标配置（不改活动 ICC），保留 sRGB 原色矩阵及白点。独立参考为 `sqrt(sRGB_EOTF(source))`，并检查低亮色块发生非恒等变化，避免“ICC 没执行但输出一样”也算成功。

12bit 709、16bit 2020 两种 API 共四组，实际 ICC 管线最大色块平均编码误差约 0.001217／0.001953，均满足本轮 `<0.002` 的平均误差预算。验证了配置管理器到实际 GPU ICC 变换与 RGB10 输出的连接；没有用两种后端一致作为 ICC 数学参考。

## 7. 真实 OP 样片

OP 首帧为黑场，已舍弃其作为色彩运算验收的用途，改测第 5 秒有颜色的帧。独立 FFmpeg 解码与 mpv dav1d GPU 上传：两种 API 的全部 **24,883,200 个 Y／Cb／Cr 整数样本逐字节相同**。

源参数实际为 yuv444p12、有限范围、BT.709、BT.1886。第一张 3840×2160 RGBA16F 写回在缩小前已完成矩阵解码及线性化。108 个空间位置、324 个 RGB 分量对独立公式的最大误差 **0.000239753**；参考范围约 0.000994～0.394821，确认不是全黑测试。

这里的线性工作量以 203 nit 为单位，受控 SDR 白为 80 nit，所以参考是 `max(RGB,0)^2.4×80/203`；后续 scRGB 输出编码再乘 `203/80`。若把中间工作单位直接当成最终 scRGB，会产生错误的验收结论。

这份 OP 是有限范围，未触发全范围中点错误。源上传与其矩阵／线性化通过，并不证明任意 10／12bit 全范围片源都准确。
