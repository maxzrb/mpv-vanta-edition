# HQ HDR→SDR 偏暗：静态审计（2026-11-14）

本轮用户提供左右对照图，反馈 HQ 高色准 HDR→SDR 整体偏暗、亮部不足、暗部层次差；HDR 手机观感更接近右侧。随后用户明确正在游戏、不可测试，因此本轮只读源码、文档和既有记录，没有启动 mpv、FFmpeg、GPU 回读或性能测试，没有修改播放配置。

## 已确认的实现与验收缺口

1. `portable_config/scripts/color-target.lua` 的 `SdrValues` 强制 `hdr-compute-peak=no`，并由 `HdrValues`、`SdrManaged` 复用。此策略并未按普通 HDR10、HLG 与带动态元数据的源区分。它来自 11 月 13 日对另一部 Dolby Vision 影片亮度变化的修正，不能据此证明对所有 HDR→SDR 内容最优。
2. HQ 使用 `hdr-contrast-recovery=0`，标准模式为 0.30。这是映射后的局部对比恢复差异，不足以单独证明整体偏暗的原因；关闭此项也不构成“更准确”的独立证据。
3. SDR ACM 路线把有效系统 `sdr_white_nits` 同时写入 `target-peak`、`hdr-reference-white`，缺失回退 80，并采用 FP16/scRGB。既有实机记录报告 80；本轮未查询显示器或活动播放器，不能把历史数值当作截图时的实测状态。工作空间编码白位、映射目标和面板物理峰值需要分别验证，不能直接以驱动 270 或固定 203 替换。
4. `tools/test-hq-sdr-fate.py` 的 SDR 灰阶有独立 sRGB EOTF 参考；PQ 部分只比较同一 40 nits 灰块在两种周边下的输出差异，没有对该灰块的映射亮度设置独立参考，也没有验收 HDR→SDR 暗阶分离、中灰及高光利用率。因此通过这组 FATE 不能证明 HDR→SDR 亮度分配合理。
5. 图像可直接观察到左侧天空及轮廓较暗；截图不能区分数值黑位剪切与较低亮度下不可见的层次，也不能证明手机/右侧播放器是作者参考版本。右侧标题的 HDR 字样不能替代 ffprobe 对实际静态/动态元数据的识别。

## 官方定义

mpv 官方手册明确：`hdr-compute-peak` 从逐帧图像计算峰值/平均值，替代对标记元数据的依赖；`hdr-contrast-recovery` 是色调映射后的对比增强；`hdr-reference-white` 与 `target-peak` 具有不同定义，不能单凭数值推断物理发光亮度。
