# 色彩与播放性能继续优化研判

日期：2026-10-05。方向：公开配置、多种硬件、稳健默认与可选模式。本轮完成审查和隔离回归，没有修改活动播放配置、脚本、核心、驱动或 Windows HDR，没有发布。原工作区未提交改动保留。

## 总体判断与路线概览

色彩准确与性能可以同时改善：保持正确的范围、矩阵、原色、传递函数及亮度标尺，减少不必要的拷贝、重复重建和额外处理。不过，HDR 映射、空间缩放与时间插值各有取舍，不能用一个“最高画质”预设覆盖所有设备。

建议分开管理显示目标、解码路径和可选增强。显示目标由显示器模式、Windows 色彩管理和校准决定；解码路径由编码、GPU、渲染接口和滤镜需求决定；性能模式主要调整处理成本。改变性能档位不能顺带改写源范围、传递函数、HDR 白点或用户的音视频同步策略。

| 环境 | 准确播放的实现路线 | 性能与兼容路线 | 验收重点 |
|---|---|---|---|
| SDR，已确认的 sRGB 显示模式 | gpu-next 高精度处理，目标与实际显示曲线匹配，按输出抖动 | D3D11；比较直接与 copy 硬解；增强默认关闭 | 灰阶、范围端点、色块、实际屏幕曲线 |
| SDR，广色域屏，Windows ACM 关闭 | 使用对应当前显示器和模式的可信 ICC，或用户确认的硬件 sRGB 模式 | ICC 缓存与跨屏更新；缺失配置时显示未校准 | 过饱和、ICC 加载和显示器模式匹配 |
| SDR，Windows ACM／Advanced Color 开启 | 明确 Windows 与 mpv 的转换责任，验证输出标记和 ICC 行为 | 使用经过设备验收的系统色彩管理路线 | 重复转换、跨屏、系统开关变化 |
| HDR 内容→SDR 屏 | 明确执行 tone／gamut mapping，准确范围和色彩解释为基线 | 先测峰值分析与缩放成本，再选择可选轻量参数 | 小面积高光、场景切换、黑位和色带 |
| HDR 内容→HDR 屏 | 校准目标峰值、黑位和白点；分别验收 scRGB 和 PQ；区分 mpv 适配与交给下游映射 | 尽量保持同一输出链，失败有界回退 | 实际输出协商、PQ／HLG 亮度、重复映射 |
| SDR 内容→HDR 桌面 | 保留 SDR 语义与参考白；反向扩展动态范围作为独立观感选项 | SDR／HDR 切集尽量复用当前 HDR 输出链 | SDR 白点、字幕／OSD 亮度、模式残留 |

HDR→SDR 的亮度和色域压缩有不同合理选择，无法保证与 HDR 母版视觉完全相同。scRGB 的 BT.709 原色是线性容器描述，不能据此认定输出已裁成 SDR 色域；是否保留负值、超范围颜色及绝对亮度仍需回读。软件回归和面板色准验收分开记录。

Windows 传统 SDR 与 Advanced Color 的色彩管理责任不同；系统 ICC 的查询与使用行为也会变化。因此“对所有用户自动开启 ICC”缺少适用条件。[Microsoft Advanced Color 与 ICC](https://learn.microsoft.com/en-us/windows/win32/wcs/advanced-color-icc-profiles)

## 已有基础，不重复实施

当前核心：mpv v0.41.0-1095-g413ff0b1c、FFmpeg N-127165-g12c589a37、libplacebo v7.374.0，2026-10-04 构建。本机此前记录为 Windows 11、RX 6600、SDR sRGB 显示模式。

- 活动基线为 gpu-next／D3D11、BT.709／sRGB 目标、fruit 抖动；默认没有 AI、时间插值、Shader 增强或去色带。
- `HDR2SDR` 的额外局部对比度恢复已经关闭，旧强度保留为手动观感选项。
- 已有统一色彩目标管理器、能力门禁、scRGB→PQ→SDR 回退、有限验证超时，以及对多数色彩选项的恢复所有权判断。
- 大分辨率硬解选择已经提前到 `on_preloaded`，采用文件局部设置，避免首次解码后再改变硬解；默认同步没有被该规则覆盖。
- 原有高位深灰阶、范围端点、HDR 数学、普通播放与部分生命周期验证可继续使用。历史结果见 [实施与验证](色彩优化实施与验证.md)。

这些基础应保留。公开默认仍需要明确适用条件：sRGB 目标适合已确认的 sRGB 环境，不能承诺未经校准的广色域屏也准确。

## 本轮确认的状态缺口

补充夹具复用现有 Lua 回归，对相同活动脚本做隔离故障注入。以下描述的是代码行为，不代表真实 HDR 显示器已经发生同样故障。摘要和活动文件 SHA-256 见 [证据](continued-audit-results-20261005.json)。

| 优先级 | 发现与复现 | 影响与建议 |
|---|---|---|
| P0 | `Restore()` 某项写入失败仍清空 baseline／owned；上层可显示“可用”。注入 target-trc 恢复失败后，仍为 scRGB，第二次恢复也无基线可用 | 恢复失败应返回并汇总错误，保留未恢复项与重试能力；不能报告成功 |
| P0 | 同显示器、同 HDR 目标的 `file-loaded` 仍调用内部选择；`Update()` 因恢复原格式再重新应用而撤下视频轨 | 为切集减少重复 VO／解码器重建；只在最终所需输出参数变化时重建，切集刷新验证即可。保留必要重建时的暂停／轨道保护 |
| P1 | 已选 SDR 后外部修改 target-trc，再选择 SDR 被重复选择捷径直接返回；状态仍为 SDR／可用 | 真实 IPC 也复现 gamma2.2 请求保留。应区分“目标意图”“实际选项”“外部改写”，同模式重选的行为应明确，幂等不等于跳过一致性检查 |
| P1 | 显示签名只包含 UID、HDR 状态、最大／最小亮度；仅 hdr-supported 从 true 变 false 时不重新检查 | 签名及能力状态需要完整失效规则；后续结合色彩空间、ACM、白点／校准变化。缺少原生信息时保持未知 |
| P1 | 开启轻量插值后，用户改 video-sync 为 display-tempo；`quality-reset` 将其恢复为先前 audio | 增强模块也需要比较当前值与最后写入值，再决定是否恢复，保留用户后续选择 |
| P1 | 推荐增强拒绝 HDR／广色域；专家 `quality-shader-command` 在 PQ 下仍执行 FSRCNNX | 这是门禁覆盖差异，不证明该 Shader 必然错色。保留专家自由，但显示未验证提示，并明确推荐安全入口与专家覆盖入口 |

另有三个可从配置直接确认的改进机会：

1. `input.conf` 的 ICC、target-trc、colorspace hint 等快捷入口会绕过管理器。管理器要能观察并报告外部改写，或让常规入口委托管理器；专家修改仍应保留。
2. 菜单把峰值计算称为“HDR 动态映射”，把 colorspace hint 称为“HDR 直通”，容易让用户误判处理已执行。建议显示峰值分析、输出标记和实际目标；动态格式识别、RPU／FEL／动态元数据处理、最终输出分别报告。
3. `persist_properties.conf` 仍包含 `vf`、tone-mapping、hdr-compute-peak、参考白和 hr-seek-framedrop。`vf` 应明确是否属于跨启动偏好，并排除临时增强标签。当前本机持久化 `vf` 为空、相关映射参数为 auto，没有证据证明本次普通播放已受到残留滤镜影响。既有个人设置不直接删除。

## 值得测试的性能优化

### 直接硬解与 copy 路径按需求选择

普通视频目前默认 `d3d11va-copy`；大分辨率才选择直接硬解。值得在无 CPU 滤镜的 1080p／4K 高帧率播放中比较直接 D3D11VA，特别是独显的数据下载和再上传成本；VapourSynth、软件滤镜或互操作不兼容时使用 copy／软件回退。不能按“所有滤镜都不支持直接硬解”或“直接硬解就是完全零复制”来设计。

P010 的紧密存储估算：4K 一帧约 24.9 MB，60fps 单方向约 1.49 GB/s；8K 一帧约 99.5 MB，60fps 单方向约 5.97 GB/s。它只是尺寸×字节数估算，未计对齐、实际下载格式、驱动缓存或架构差异，不是测得的总线吞吐。核显共享内存和独显应分别测试。

推荐先比较 Windows D3D11 路线，Vulkan 保留明确适配的可选路线；每次记录实际 `hwdec-current`，不能把请求硬解但实际软解的结果作为后端对比。保留正常 GPU→GPU 复制；不要全局开启有边缘采样和驱动风险的 `d3d11va-zero-copy`，也不要把 VS 播放器的队列补丁移植为 mpv 配置。[mpv 硬解及 D3D11 选项](https://mpv.io/manual/master/#options-hwdec)

### 缩放与 HDR 映射分开计量

现有 EWA 放大、Catmull-Rom 缩小、bilinear 色度恢复是一个取舍。候选档位可为“稳健默认／低功耗／高质量”，只改变缩放、可选去色带和插值等成本，不改源色彩解释。高质量候选可研究色度恢复和线性缩小；低功耗候选要确认边缘、细字和彩色线条质量，不能以 GPU 负载低就判优。

HDR 峰值分析目前为 auto、百分位 99.995、即时检测。可以比较 100 百分位、元数据路线、延迟检测及不同缩放尺寸的开销，但它们会影响孤立高光与场景过渡。先做图块／快切／seek 后恢复测试，再决定是否提供低功耗选项，暂不把任何候选升为准确基线。[mpv HDR 峰值检测](https://mpv.io/manual/master/#options-hdr-compute-peak)

全局 `hr-seek-framedrop=no` 值得单独比较长 GOP 跳转延迟；保留逐帧准确需求对应入口。网络缓存按码率、延迟和可定位性测试，不以扩大缓存修复渲染瓶颈。起播徽标、缩略图和黑边探测的外部采样只在启动压力实验中计量，现有个人 Logo 参数保留。

同步方面保留 audio 为稳健基线；display-resample／时间插值为可选路线，测试固定帧率、VFR、高刷新率、音频直通及跨屏。不能通过关闭丢帧、减慢媒体时钟或关闭同步把“零丢帧计数”作为实时播放改善。

### 性能验收方法

先确认源编码／位深／帧率、实际解码路径和渲染目标，再区分解码、拷贝／滤镜、GPU 处理、呈现／同步和网络供给。相同素材、窗口、刷新率、音轨、字幕、配置，每组至少三轮，启动／跳转与稳定播放分段。

记录墙钟／媒体推进比、丢帧增量、音频欠载、A/V 偏差、CPU／GPU／显存、首帧和 seek 恢复时间。具备逐帧追踪时记录呈现间隔和长尾；`vo-passes` 的平均值不能冒充单帧总时长或 P95，不把重叠执行阶段简单相加。

## HDR 和跨设备的剩余验收

优先建立可持续播放的 HDR10／HLG 基础素材，再增加 Dolby Vision P5／P8／P7 MEL／FEL、HDR10+。格式名称显示成功不等于完整动态处理成功，失败回退是否语义正确应按格式分别确认；例如不能对所有 DV 都假定有可直接观看的 HDR10 基础层。

需要 AMD／NVIDIA／Intel 各至少一台实机，覆盖集显／独显、SDR／HDR、混合多屏、热插拔、系统 HDR 切换、全屏、不可定位流、损坏文件、硬解回退、字幕和长时播放。用户手动峰值应绑定显示器身份和模式，避免把同一个数值无条件套用到下一块屏幕。

HDR 应核查峰值、全屏持续亮度、黑位、参考白、校准来源及映射责任。用 PQ 灰阶／HLG 彩色块／宽色域向量做软件回读，再用仪器验证亮度曲线与色差；SDR 可报告 ΔE00，HDR 可报告 ΔE_ITP。没有显示器和测量仪时，只能声称软件回归或输出协商通过。Windows 的 scRGB／HDR 行为依据见 [Microsoft DirectX Advanced Color](https://learn.microsoft.com/en-us/windows/win32/direct3darticles/high-dynamic-range)。
