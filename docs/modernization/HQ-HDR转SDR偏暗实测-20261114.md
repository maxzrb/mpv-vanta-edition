# HQ HDR→SDR 偏暗实测（2026-11-14 23:59，Asia/Shanghai）

## 结论与范围

用户恢复测试授权后，对《The Odyssey》约 01:27:05.820 的原片及冻结帧完成检查。已证实当前静态源峰值选择是本段显著压暗的一个因果环节：输入同时有母版峰值 1000 nits 和内容 MaxCLL 97 nits，libplacebo 先取母版峰值，导致当前 80 nits 输出下的样条提前压缩中高亮度。仅改变送入映射器的源峰值边界即可显著恢复天空亮度，其他 HQ 管理器选项和输出目标逐项相同。

这次没有把用户已排除的逐帧峰值检测、对比恢复开关重新作为原因。两组始终 hdr-compute-peak=no、hdr-contrast-recovery=0、target-peak=80、hdr-reference-white=80，FP16/scRGB 输出。没有修改生产播放配置，也没有实现自动 MaxCLL 修正。

## 原片与冻结帧

- BT.2020 / PQ / 有限范围 / HEVC 10-bit / 3840×2160。母版峰值 1000、最低亮度 0.001、MaxCLL 97、MaxFALL 55 nits；未见 Dolby Vision 标记。
- 独立 FFmpeg 解码此帧，按有限量程、2020 NCL 矩阵和 ST 2084 解算，最高 RGB 通道约 77.2017 nits。此值是该帧 RGB 通道最大值，不是整片扫描、MaxCLL 认证或面板亮度。
- 原始解码帧冻结为 FFV1，解码回原 YUV 与原帧逐字节一致，SHA256：63950393f7de31c9378b1aafd169eb5fb0621695544c437c838c3689f4f4e76f。
- 冻结帧两组使用同一视频、同一缩放和同一输出；只用 format 元数据覆盖改变映射边界 1000→97，保持 PQ、色域、有限范围和原像素格式。最终逐项核对管理器设置和 video-target-params 相同。
- FP16 交换链读回在 Windows 合成之前已显示显著差异。两组最大 RGB 通道分别约 0.36987 与 0.86963。不能仅据此排除 Windows 合成还存在其他影响。

## VSP 对照

用户提供的目录实际为 Full 1.1.3，player.ini 的 color/engine=0，即 3FP 原生；SDR peak=100、paper white=203。未启动或操作 VSP GUI，未修改其 INI。

固定上游 HdrProcessor::StaticSourcePeak 优先 MaxCLL，其次母版峰值；随后源峰值还会以 paperWhiteNits 为下界钳制。因此不能将 VSP 的有效边界简单说成恰好 97；其原生 BT.2390 曲线和输出设置也与 mpv 样条不同。本机实际 DLL 的 FFF3FP_EvaluateColorTransform 无窗口接口已调用成功，数值明细及 DLL SHA 留在 vsp-native-numeric.json。此接口是生产转换的数值探针，未读取 VSP 实际交换链，不声称已与用户右图逐像素匹配。

## 后续修复边界

应针对静态 HDR→SDR 建立源内容峰值的选择策略，保留真实母版元数据，不用无条件改母版、全局提亮或改系统白位替代。MaxCLL 可能缺失或错误，需要限定适用范围、记录所选边界与回退原因，并与 HDR10+/DV 动态元数据及 HDR 输出隔离验收。当前实验证明该段的压暗机制；尚未证明自动采用任意 MaxCLL 对所有视频都更准确，也没有解决完整映射策略的所有问题。
