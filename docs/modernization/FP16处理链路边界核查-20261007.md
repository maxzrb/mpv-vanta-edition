# FP16 处理链路边界核查（2026-10-07）

## 结论

当前配置使用 gpu-next／D3D11；普通 GPU 渲染优先使用 FP16 中间缓冲。本机已有二进制日志在 SDR8、SDR10、广色域 SDR、HDR10、HLG 五类素材的默认输出与显式 scRGB 两组中均记录实际创建 rgba16hf 与 rgb16hf。不能将这个证据扩展成所有滤镜、所有硬件、所有中间资源必定 FP16。

本次复查读取既有独立播放器日志和当前配置／Shader，不启动新播放器，不新增起播扫描、解锁或普通流程检查，不改变运行配置。

## 阶段与边界

| 阶段 | 格式含义与风险 |
|---|---|
| 解码输入／上传 | NV12／P010 等保留源编码；r8／r16 源平面不等于 RGB 运算中途降精度。P010 有效数据为 10bit，容器存储 16bit。 |
| 普通 GPU 渲染 | 高精度 RGB 中间结果优先 FP16，Shader 运算精度与纹理存储精度分开。合并多个步骤可以减少中间写回，不表示链路断开。 |
| VapourSynth／外部模型 | 位于渲染器之前，按模型与桥接格式处理，可能回到整数 YUV；SVP 使用原有 8／10bit 策略。后续转回 FP16 不能恢复已量化的信息。用户明确允许为模型效果、性能和兼容性保留这些边界。 |
| 最终交换链 | SDR 可输出整数 8／10bit，HDR scRGB 使用 FP16；输出格式不证明所有内部处理格式，也不保证系统／驱动到面板全程 FP16。 |

libplacebo 上游 renderer 格式选择依次优先可渲染 FP16，然后兼容回退至 16bit 整数、8bit。设备能力、FBO 错误、显式低位深选项等可改变路径。当前配置未发现启用 force_low_bit_depth_fbos／disable_fbos 的覆盖；相关源码只是上游实现解释，不冒充随附二进制每个阶段的精确构建映射。

mpv 官方说明 gpu-next 的中间缓冲由 libplacebo 管理，fbo-format 不作为此渲染器的控制入口，因此添加 fbo-format=rgba16f 不构成全链路保证。[GPU Next 与 GPU](https://github.com/mpv-player/mpv/wiki/GPU-Next-vs-GPU)；[libplacebo renderer](https://github.com/haasn/libplacebo/blob/master/src/renderer.c)。

## Shader 声明复查

当前 GLSL 中找到十处低位深 FORMAT 声明：SMAA 的 AREA_TEX／SEARCH_TEX、HQX 的权重查找表、harmony 的三张叠加素材；全部属于显式 TEXTURE 数据。这些声明本身没有要求主视频输出改成 8bit，也不构成对所有 Shader 数学处理、截断或量化行为的完整证明。不能把辅助查找表按主图像缓冲统计。

## 证据范围

复查十份既有日志的实际 texture creation 事件，而不是 GPU 支持格式枚举。十份都有 rgba16hf、rgb16hf；HDR 日志另有 r16hf 和 r32f 等分析资源。日志还会出现源平面、OSD／查找资源的 r8／r16，不应一概解释为主图像降级。日志保存在忽略的 tmp/modernization/validation，不复制媒体路径到公开记录。

本轮不新增性能收益结论。FP16 缓冲在现代 GPU 上通常可高效使用，但相较 RGBA8 占用更多存储与带宽；多次全帧写回、分辨率与滤镜数量会影响实际成本。当前普通渲染本已使用它，不需要重复加开关。

若继续增强可观察性，应区分源格式、滤镜交接格式、内部缓冲证据与最终输出，并在手动诊断中采集详细纹理／pass 信息。现有 video-target-params 或 16bit PNG 截图单独不足以证明整条链路未量化。
