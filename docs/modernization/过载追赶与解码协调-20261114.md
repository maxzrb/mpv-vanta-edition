# 通用过载追赶与解码协调

本地功能已实现。菜单入口为「视频 → 播放性能 → 过载追赶（省略部分画面）」，默认关闭；用户开启后，软件解码持续落后或持续掉帧时进入 `nonref`，默认保持到本片结束。该策略减少需要解码的画面数量，不改变剩余画面的位深、色度、缩放或色彩目标，也不把输出称作原始全帧播放。

仅保存 `files/playback-preferences.json` 中的 `overload-catchup` 布尔开关。临时 `vd-lavc-skipframe=nonref` 和视频轨操作均使用文件局部选项，不跨文件／重启保留。现有播放窗口需要退出并重新打开，才能加载更新后的脚本和菜单。本功能纳入 v1.6.7 发布候选，默认仍需用户主动开启。

## 默认判定与恢复

| 条件 | 默认值与行为 |
|---|---|
| 进入追赶 | 视频落后至少 350 ms，连续维持至少 1.5 秒 |
| 掉帧触发 | 完整解码时，2 秒统计窗口掉帧至少 3 帧、占源帧率×速度×窗口的至少 5%，且持续 1.5 秒；停止增加计数不继续累积过载时间 |
| 操作保护 | 暂停、跳转、变速、缓存等待及重建后重新等待 2 秒 |
| 默认保持 | `catchup_recover=no`；追上声音不自动退出，暂停／变速／用户跳转也不主动恢复完整解码；换片清除临时模式 |
| 可选自动恢复 | 显式设置 `catchup_recover=yes`；绝对声画差不超过 60 ms，稳定至少 8 秒，参考帧模式驻留至少 12 秒 |
| 可选恢复重试 | 初始间隔至少 30 秒；重试后很快再次过载，间隔指数延长至 60／120／240 秒 |
| 模式内重新同步 | 参考帧模式仍落后至少 750 ms、持续 2 秒：仅精确定位，不撤轨／改跳帧参数／重新创建解码器；进入后至少 10 秒，完成后间隔 10／20／40／60 秒退避 |
| 无音轨视频 | 使用媒体位置与墙钟差，暂停／跳转／变速后重新建立锚点 |
| 用户操作 | 关闭开关恢复完整解码；明确选择解码方式优先于自动追赶；停止／换片取消过期事务 |
| 所有权 | 命令行和文件专用跳帧参数优先；外部修改受管参数后，本文件不再自动抢回 |

硬解、不可定位流、纯帧内编码，以及需要完整输入的 VapourSynth／RIFE 等时域处理不主动启用参考帧追赶。这些是运行条件保护，不以编码名称限定为仅 AV1。已实际覆盖 AV1、H.264、HEVC 和 VP9 的软件模式切换及硬解隔离。

默认保持的依据是：参考帧模式下同步恢复，只能说明减少画面后处理得过来，不能证明全帧解码达到实时速度。本机一次解码模式重建耗时约 3～4.5 秒，频繁恢复探测会造成额外停顿。代价是后续简单场景也继续省略非参考画面；需要全帧或精确逐帧检查时，关闭追赶开关恢复。模式内重新同步仍有定位／预解码成本；参考帧本身也不及实时速度时，只能舍弃落后内容，不能让解码器凭空变快。

VSP 1.0.16 对应[实现](https://github.com/user-Wing/VS-Renderer-GUI/blob/deefd4f8effc028e2bfea69fca10e859d8ff16cd/patches/3fp-api20-vsrenderer-1.0.10.patch)在独立关键包处判定：8K libdav1d 软解、恒定帧率、落后超过 250 ms 时进入；参考帧模式落后小于 75 ms 时退出。`DoSeek` 也恢复完整解码，不采用本片锁定。它先创建新解码器再替换旧实例，保留当前文件／音轨，不做这里的全局回溯定位；仍有创建／切换成本，未测得具体停顿时长。

## 与现有管线的协调

`decode-performance.lua` 统一串行处理追赶与硬解选择，保留既有工作线程、帧并行预算、轨道选择、字幕、暂停与日常跳转偏好，不为追赶额外加线程。

原地切换在一个核心命令批次中暂停播放、暂时撤下视频轨、定位到安全位置、设置文件局部跳帧模式、恢复原视频轨并精确定位，然后恢复原暂停状态。以首帧 `playback-restart` 确认完成，保留当前文件及音轨；等待超时才回退整文件安全重载。手动硬解选择可以抢占自动事务。

直接修改跳帧选项再定位的对照，在四种编码上分别复现 AV1 OBU、H.264 MMCO、HEVC RPS 和 VP9 缺少参考帧错误，未采用。原地撤轨方案在四种编码、两种图形后端及无音轨条件下无此类错误。

当前 [FFmpeg libdav1d 包装层](https://github.com/FFmpeg/FFmpeg/blob/b2b543c07/libavcodec/libdav1d.c)在初始化时设置 `decode_frame_type`；[dav1d 公共接口](https://github.com/videolan/dav1d/blob/master/include/dav1d/dav1d.h)没有在现有上下文上热切换该设置的入口。因此这里采用安全重建与定位，保留预解码开销，没有宣称无缝热切换。

色彩输出重建现在通过 `user-data/color-output-rebuilding` 发布忙碌状态，解码事务通过 `user-data/decode-performance/reload-active` 发布状态。起播徽标取消尚未完成的截图并等待可截图的新帧。画质切换暂时撤轨时，追赶控制保留参数所有权，等待视频恢复后再处理关闭／还原，避免误把暂时无视频当成文件结束。

- WASAPI 输出管线保留，音量设为 0，未做物理录音。关闭组观测 30 秒；开启组前 30 秒同为 1 倍速，此后的 0.25 倍速仅降低解码需求以验证恢复，不计入正常速度性能统计。

|---|---:|---:|---:|---:|
| D3D11 | 13.258 秒 | 79.670 ms | -0.246 ms | 0／0 |
| Vulkan | 12.960 秒 | 52.451 ms | -0.008 ms | 0／0 |

同步误差与切换停顿分开记录：定位期间暂停输出，误差读数不能代表连续呈现。此片进入／恢复完整解码的实测耗时，D3D11 为 3.617／4.499 秒，Vulkan 为 3.954／3.248 秒；长 GOP 预解码仍会造成数秒停顿。所有组无错误级日志；两后端都在降低解码需求后自动恢复完整解码。这是改为默认保持前的基线；当前复现该自动恢复行为需传入 `--auto-recover`。

切换前、参考帧模式及恢复完整解码后的观测均保留：7680×4320／`yuv420p10` 源格式、HQ、`rgba16hf`／scRGB 目标和原线程／帧并行选项，没有用降位深或关闭 HQ 换取上述结果。

## 默认保持策略的实片复核

使用最近用户日志中的 `OP-yuv444p12-SWTest.mkv`：3840×2160、约 47.952 fps、AV1 12-bit 4:4:4，保留内封 ASS、完整 HQ 与原生日常解码预算。关闭组 30 秒，开启组 70 秒；30 秒后仅开启组降至 0.25 倍速验证低负担后仍保持模式，后段不计入正常速度性能。

| 后端 | 关闭组 8～30 秒最大绝对声画差 | 开启组 8～30 秒最大绝对声画差 | 关闭／开启日志音频欠载 |
|---|---:|---:|---:|
| D3D11 | 285.070 ms | 113.468 ms | 4／2 |
| Vulkan | 881.356 ms | 0.050 ms | 2／2 |

两后端开启组均进入参考帧模式，观测结束仍为 `nonref`，模式切换数保持 1。D3D11 关闭组声画差始终未到旧版 350 ms 触发线，结束时累计 VO 掉帧 670，说明只看声画差确实会漏检供帧不足。VO 掉帧也可能来自字幕／渲染等环节，不能用该计数单独断定 CPU 解码是唯一瓶颈。开启组仍有音频欠载，本次不声称已修复音频稳定性；模式切换会重置掉帧计数，不能把前后累计数直接当作吞吐率比较。

该实片未自然触发模式内重新同步；重复重新同步由固定传感快照的真实核心测试验证。详细采样分别在 `backup/overload-followup-20261114/d3d11-sticky.json`（关闭组）、`d3d11-sticky-final.json`（最终开启组）和 `vulkan-sticky.json`。D3D11 开启组在瞬态掉帧保护细化后重新跑过，旧开启组不作为最终数据；两个后端最终开启组使用的策略文件 SHA 与当前源码一致。

最近保存的用户日志 `user-playback.log` 中没有 nonref 切换，`catchup-switches` 全为 0；该日志不能用于确认用户描述的更早一次切换事件。状态页现区分“追赶模式切换”和“模式内重新同步”，保持同一模式时后者增加、前者不增加。

## 切换耗时的口径澄清

此前的 3～4.5 秒是模式切换请求至播放恢复的总耗时，不能当作创建解码器本身的耗时。8K 基线 D3D11 日志显示：5.467 秒打开并选定 libdav1d，5.469 秒启动到 8.913225 秒的精确定位，5.648 秒记录解码输出格式，8.954 秒视频输出重新配置到 8K，9.077 秒重启后首帧显示，9.084 秒声画播放恢复。定位从 5.986 秒的关键位置重新处理至约 8.913 秒，跨越约 2.93 秒片段；同时经历输出重新配置和 shader 编译，尚未对每阶段 CPU/GPU 耗时独立插桩，不能把全部等待归于初始化或某一次 shader 编译。

当前 Lua 方案撤轨后创建新解码路径，再做全局精确定位，会清理／重新准备音频输出；日志有 WASAPI Reset/Pause/Resume。VSP 在当前读到的独立关键包处先打开新上下文、再停止并替换旧解码器，不全局定位、不主动暂停整个播放，因此少了上述回溯和全局同步成本。VSP 主观接近无感有源码依据，不以未测量为由否定该体验。改进方向应是核心内关键包边界切换、保持音频时钟和输出；Lua 的本片保持仅减少重复付出切换成本，不等同已经实现该切换机制。

开关记忆与临时模式不同：保存的 `overload-catchup=true` 在每次启动恢复，所有后续视频均自动监测；每个新视频从完整解码开始，只有过载才进入参考帧模式。当前个人开关为 true，并非每部视频都要重新开启菜单。
