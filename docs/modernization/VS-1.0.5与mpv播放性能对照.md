## 方法与指标含义

串行启动，每组独立进程，跳到 10 秒，播放至媒体位置 15 秒后开始采样；目标每秒读取一次，稳定段约 20 秒，每组重复三次，共完成 39 次独立试验。软解高负载下 mpv IPC 有延迟，每轮实际为 14–15 个样本，其余组为 21 个；速率与 CPU 使用实际墙钟差归一，软解数值只作近似吞吐比较。初轮探查后加入进程级 PDH GPU 计数和窗口置顶；置顶复测用于排除聊天窗口遮挡导致的 DXGI 节流。`tmp/modernization/vs105-results/` 保存初轮数据，`vs105-controlled/` 保存 GPU／同步／软解复测，`vs105-color-matched/` 保存准确 sRGB 补测。

- 基础组的客户区固定 1280×720。mpv 完整配置保留窗口脚本，实际约 1238×696，单列为日常配置参考。两边音频设备保持开启但静音，字幕关闭，AI／Shader／补帧不启用。
- mpv 基础组：`gpu-next`／D3D11／`d3d11va`；Catmull-Rom 缩小、双线性色度、无去色带。轻量组改为双线性缩小并关闭正确缩小预滤波。SDR 目标为 BT.709／sRGB。
- 基础组指定 sRGB 后，默认 `treat-srgb-as-power22=yes` 仍使目标报告为 `gamma2.2`；准确 sRGB 补测明确设为 `no` 并关闭色彩空间提示，实测目标为 `srgb`。完整配置本身已关闭该近似。本轮不作两播放器等色准、等画质的保证。
- 3FP：D3D11 硬解、MapToSdr，测试 Jinc 亮度与色度（1284）、双线性亮度与色度（513）、D3D11 原生处理（7）。算法不构成等画质保证；双线性组主要用于轻量路线对照。
- 同步附加组同时请求 `SetPresentConfig(1)` 与 `SetPacingConfig(1)`。调用成功只证明接受了配置，不能证明显示器正在 VRR 扫描或实际出现 tearing。
- 软解组：mpv 强制 `hwdec=no`、16 解码线程，3FP 强制 CPU 模式；3FP 内部线程策略由该 DLL 决定。软解组使用双线性缩放，不混入补帧。
- “进度倍率”是媒体时间增量／真实墙钟增量，1.00 才是实时。3FP“净接受 fps”是接受帧减合并帧的增量／墙钟时间，不把重复 Present 当新视频帧。
- 两边丢帧计数定义不同：mpv 表中为 `frame-drop-count` 的稳定段增量，另检查解码丢帧；3FP 为自身 `droppedVideoFrames`。不能直接把两者作为同口径总丢帧率。
- CPU 是进程 CPU 时间增量；GPU 是该进程的 PDH 引擎利用率，不是整机总占用。AMD 驱动的 `Video Codec 0` 名称不保证只包含解码工作。完整 mpv 的外部子进程 CPU 不计入主进程。
- mpv 的 `estimated-vf-fps` 是处理流帧率，不是显示器扫描测量；前39次没有 PresentMon／光学测量；后续ETW呈现探针见下文，仍不能证明物理扫描出的每一帧。

### 性能差距如何解释

1. 本机在该片段上具备接近实时的 AV1 硬解能力；mpv 基础路径实测能够维持媒体速度。这个结果不能推广到所有 8K、8K60 或更复杂素材。
2. 3FP Jinc 解码计数约 46.24 fps，但净接受约 25.26 fps；双线性也约 25.73 fps。损失不只来自 Jinc 运算，表现为解码之后的丢弃／接受／呈现链无法跟上。各路径 Video Codec 引擎已接近饱和，缺乏余量。
3. 3FP 的 Present 等待约 28–38ms，明显高于源视频约 20.85ms 的单帧预算。它包含 GPU 排队、交换链／DWM／驱动同步等等待，不能解释成纯 CPU 睡眠，也不能仅凭它定位到某个函数或认定显示器只运行于某一帧率。
4. 请求 tearing＋pacing 后，Jinc 三轮净接受为 25.36–28.15 fps，未达到源速率。当前证据不支持“换同步策略就能解决”，也不支持将该正式包称为本机比 mpv 更流畅。
5. 强制软解时，两边媒体推进均约 0.6 倍速、CPU 约 12.3–12.5 核。先前 mpv 软解回退确实足以造成明显卡顿；必须区分那个初始化问题与现在保持硬解的表现。

|---|---:|---:|---:|
| 519，720p | 0.00052ms | 37.13ms | 28.25／73.38ms |

源单帧预算约20.85ms。720p原生组约52% Present超过该预算、24%超过50ms；Shader组分别约61%／32%。因此等待集中在合成／呈现及其GPU排队依赖；Shader双线性合成区间低于预算而Present仍很慢，不能把所有等待解释成缩放运算太重。原生VideoProcessor的GPU合成区间包含共享上下文解码／视频处理排队，不能当纯VideoProcessor算法耗时，**GPU区间和CPU Present等待有重叠，不能相加**。

本轮原生两次稳定段自身丢弃计数分别增加242、247，Shader增加375，tearing组增加286；mpv稳定段输出和解码丢帧增量均为0，保持`d3d11va`、1280×720、BT.709／准确sRGB／RGB10A2。mpv进入稳定段前已有58个输出丢帧，不能称为从启动到结束全程零丢帧。

**新增证据收窄了原因：**

1. 普通VS组与mpv组均为`Composed: Flip`、SyncInterval=1、AllowsTearing=0，但mpv的提交间隔接近片源20.85ms，GPU开始延迟和显示延迟显著较低。相同呈现模式并不保证相同队列行为，也不能把VS掉帧归因于这个模式本身。
2. VS已提交的帧绝大多数被ETW跟踪到显示；主要损失仍发生在提交之前，与上一轮解码／接受／迟到丢弃计数相符。没有发现DWM丢掉数百个已提交帧的证据。
3. tearing＋pacing组实际变为`Hardware: Independent Flip`、SyncInterval=0、AllowsTearing=1，598次提交全部有显示事件，但仍约30fps、286帧迟到丢弃。因此开关确实改变了呈现路径，**仍不足以恢复实时**；不能把普通DWM合成当作唯一原因。这不证明实际VRR刷新或肉眼可见撕裂。
4. 所有组HybridPresent=0，未发现跨适配器Present复制。结合活动显示核查，当前证据不支持虚拟显示或跨显卡呈现是主因。

[PresentMon指标定义](https://github.com/GameTechDev/PresentMon/blob/main/README-ConsoleApplication.md)中，CPUWait与CPUBusy是按Present划分的墙钟区间，不是线程CPU利用率，不能将mpv的CPUBusy约20.60ms理解为每帧CPU计算20ms，也不能把CPUWait直接等同于某个函数的精确等待。GPUBusy反映目标进程相关GPU引擎活动，不能当作纯Shader或VideoProcessor执行时间；GPUTime、GPULatency、DisplayLatency存在交叠，不能相加。VideoBusy在双方均报告0，而双方已确认D3D11硬解、此前PDH Video Codec约97%，故本轮无法可靠拆分视频引擎耗时，不能说解码器空闲。官方亦提示HAGS可能影响GPU计时；本机HwSchMode注册表项未设置，实际HAGS状态未确认。

当前账户已有Performance Log Users权限，未提升权限、安装服务或改组成员。PresentMon提示非管理员可能缺少其它账户／短进程信息及退出通知；本轮按已知PID捕获有效。第一次播放器结束后采集器没有自动退出，控制程序等待超时，随后仅结束自己会话并刷新得到有效CSV；已修复为主动结束自己的会话，其余4次播放器与采集器退出码均为0，结束后无遗留VantaVSProbe会话。

剩余需要精确定位的是解码纹理生命周期／资源依赖、视频处理与解码共享GPU队列、驱动提交和帧延迟控制的相互影响。PresentMon已证明延迟差异和实际呈现模式，但没有逐GPU包／线程调用栈，不能据此指定某个驱动函数为根因。下一层需GPUView级调度轨迹或可映射的原生源码构建；优先增加帧ID关联、纹理slice获取／释放、VideoProcessorBlt、提交完成栅栏、Present进入／退出、帧延迟等待的QPC及GPU时间戳，避免只增加总占用探针。

### 已定位的队列预算问题：8K硬解提前量不足

正式DLL的RVA `0x9310`实现与公开源码的`VideoFrameQueueLimit`相符：按最后一个AVFrame的可见尺寸和软件像素格式估算单帧字节数，以128MiB除以该值，再限制为2到8帧。RVA `0x93ba`可核验为`mov eax, 0x08000000`，不是推测出来的配置入口。7680×4320 P010约94.92MiB，因此该策略落到两帧下限；源码的饱和判断又使用`queueLimit - 1`。原预算稳定段快照队列只见0–1帧，限制了渲染前的解码提前量。

仅在测试进程中把预算改为398,131,200字节，对该素材形成四帧上限，Shader两次分别47.9435／47.9480fps、丢帧和音频欠载0，快照队列稳定为2帧。恢复原预算的同探针对照立即回到22.9486fps、丢487帧、欠载11次。八帧上限Shader／原生VideoProcessor也分别47.9400／47.9582fps、零丢帧、零欠载、零合并帧，时钟均约1.00005倍。Shader四帧和原生八帧统计均保留完整像素处理，未跳过复制／Draw／VP，未降低解码或窗口尺寸；Shader八帧Present均值从约41ms降至7.26ms。

已核验的本机因果结论是：这版内核将按完整解码图像计算的内存预算应用到8K硬件帧队列，导致解码提前量不足，放大图形读取解码表面的等待和Present背压。改变预算可消除本机同片源的问题；这比仅指出“驱动等待”更具体。硬件AVFrame引用共享既有解码表面，CPU队列长度与另行分配完整图像的内存成本不能简单等同。无Frida三轮复测和修改后的精确ETW均已通过；其他片源与通用源码修复需要独立验证。

### 为什么不能用显卡规模推断780M应更慢

RX6600为RDNA2，780M为RDNA3；3D计算单元规模不等于媒体解码／视频处理能力。AMD将[视频编解码媒体能力](https://www.amd.com/en/products/graphics/radeon-for-creators/video-editing.html)与计算规格分列；架构可参考[RX6600官方说明](https://ir.amd.com/news-events/press-releases/detail/1023/amd-radeon-rx-6600-graphics-card-delivers-incredible-high-refresh-rate-1080p-gaming)与[AMD的780M规格](https://rocm.docs.amd.com/en/docs-7.2.0/reference/gpu-arch-specs.html)。不同媒体实现和驱动可有不同同步／队列表现，但不能仅凭代际证明780M必然更快。

本机驱动32.0.21045.5002，作者780M记录32.0.21030.2001；输出分别1080p165Hz环境和4K60Hz环境，DLL及编码片段也未完全对齐。本机从720p改1080p仍约30fps，未发现这一区间缩小比例是主要解释，但没有4K物理显示复现，不能排除更大输出尺寸／刷新环境影响。已核查活动主显示为RX6600驱动的ASUS输出；GameViewer虚拟显示驱动存在但未连接桌面，不据其存在判定跨适配器呈现。

目前最有证据的解释是**这版3FP的RX6600渲染／呈现链未有效维持源速率，已解码帧因迟到而丢弃**。新增ETW和预算因果控制进一步将本机该片源问题定位到8K硬解帧队列限制；仅改变预算即可恢复实时，详见前节。不同机器／驱动的表现仍需分别验证。
