# 色彩精度核查与 3FPlayer 对照（2026-10-07）

结论：普通播放的色彩目标管理与 FP16 渲染已有实现和限定范围的验证；包含增强滤镜的完整精度链路尚未完成。不能将此前功能／性能回归通过解释为所有滤镜色彩准确，也不能宣称已达到或超过 3FPlayer 的显示色准。

本轮核查不修改播放默认、滤镜后端或运行库，不增加组件扫描、播放前试跑、解锁或再次开启步骤。保留此前 SVP／裁剪／菜单修复。比较的是公开源码和本机现有结果，没有运行 3FPlayer，也没有进行共同素材下的播放器对比或仪器测量。

## 当前已验证的范围

| 项目 | 证据与边界 |
|---|---|
| 普通渲染 | 现有 SDR、广色域 SDR、HDR10、HLG 测试日志出现 `rgb16hf`／`rgba16hf` 纹理；证明这些路径创建了 FP16 纹理，不证明每个处理步骤、外挂滤镜、输出及面板都是 16bit。 |
| 色彩目标管理 | 已回归 SDR 基线、scRGB→PQ→SDR 选择、手动／外部覆盖、恢复失败重试与同目标免重建。真实 HDR 面板仍未验收。 |
| 灰阶 | `tools/validate-color-ramp.py` 使用 `--no-config` 的 gpu-next／D3D11、sRGB→sRGB GPU 高位深截图。现有结果为 1024 个灰阶均保留、最大码值误差 0。它是隔离渲染回归，不是完整配置、线性交换链回读或面板 ΔE 测量。 |
| 范围端点 | `tools/validate-color-range.py` 检查 10bit full／limited 输入端点；不等于所有原色、传递函数和亮度条件均通过独立参考比对。 |
| 数学参考 | `tools/color-reference.py` 覆盖 PQ／HLG／scRGB／矩阵数学；不是 GPU 或面板实测。 |

`gpu-next` 通过 libplacebo 管理浮点缓冲。不能通过在配置里写一个 `fbo-format=rgba16f` 就证明完整链路精度；该选项在 gpu-next 的适用性也不同于旧 gpu。[mpv 上游说明](https://github.com/mpv-player/mpv/wiki/GPU-Next-vs-GPU)

## 各阶段精度应分别描述

| 阶段 | 当前实际情况 |
|---|---|
| 解码 | 原片常见为 8／10bit，也可能是 12／16bit；提高后续缓冲位深不会补回片源不存在的信息。 |
| RIFE／AI 模型 | DML RIFE 包装使用 RGBS；部分 NVIDIA 路线使用 RGBH。模型采用 FP16 推理不等于所有输入／输出都具有同一种精度。 |
| SVP | 有 8bit 运动分析支路及 8／10bit 主图像处理路径；分析支路位深不能直接当作最终画面位深。特殊高位深／色度输入另有降格式问题。 |
| GPU 主渲染 | 已观察到 FP16 纹理。FP16 浮点与 16bit 整数具有不同的量化特性，Shader 运算精度也需独立区分。 |
| 最终输出 | SDR 格式自动选择；scRGB 请求浮点格式；PQ 回退请求 RGB10A2。操作系统、驱动、接口和面板的最终表现尚未测量。 |

## 已确认的缺口

### 1. 固定 BT.709 的滤镜转换

本机 K7sfunc 1.8.1 的 `mod_memc.py` 中，RIFE ORT 输入／回转约在 509／525 行，NV 路线约在 717／739 行，使用固定 `matrix_in_s="709"`／`matrix_s="709"`。`mod_mix.py` 的 DML／MIGX／TRT 超分入口也有相同模式。

维护阶段单独用一个 YUV444P16、limited 范围色块比较 BT.709 与 BT.2020 NCL 转 RGBS，最大 RGB 分量差为约 **0.014399**。这是模型输入差异，未运行神经模型；不将其冒充 RIFE 最终输出误差或面板色差。说明处理 BT.601／BT.2020 等输入时，必须按真实源矩阵转换，不能统一假定 BT.709。

### 2. 通用格式转换主动降低位深／色度

`Lib/site-packages/k7sfunc/mod_fmt.py` 的 `FMT_CTRL`（约 94／114 行）使用旧格式白名单。`fmt_pix=0` 并不总是原格式直通：白名单以外的输入会转为 YUV420P10。

本轮调用实际函数、请求输出帧确认：

| 输入 | `FMT_CTRL(fmt_pix=0, h_max=0)` 输出 |
|---|---|
| YUV420P8 | YUV420P8 |
| YUV420P10 | YUV420P10 |
| YUV420P12 | YUV420P10 |
| YUV420P16 | YUV420P10 |
| YUV444P16 | YUV420P10 |

因此现有“关闭格式锁定”设置还不足以保证高位深和完整色度不被降低。`mod_helper.py` 的 `FMT2YUV_SP` 对非常规输入也会统一转 YUV420P10；SVP 等后端的实际支持范围必须逐个验证，不能为宣传全程 16bit 而强制不支持的格式。

### 3. 只观察输出元数据不足以验证像素

与本机核心对应的 mpv VapourSynth 桥接源码写入 `_ColorSpace` 和 `_ColorRange`，没有直接写入现代 VS 常用的 `_Matrix`、`_Primaries`、`_Transfer`。返回帧经 `_MP_IMAGE` 继承原图属性。因此输出仍显示 BT.2020 标记，不能证明中途转换使用了正确矩阵。[对应核心源码](https://github.com/mpv-player/mpv/blob/413ff0b1cd4585294803308a1a14be2fad30cede/video/filter/vf_vapoursynth.c)

修复时要兼容桥接元数据并保留原属性；随后必须检查真实像素。直接删掉固定 709 参数、假设 zimg 能自动推断，也可能产生未知矩阵错误。

## 3FPlayer 可借鉴的实现

对照版本：`Lake1059/FFF_Project`，提交 `3fef8eb67d49da6dc92ab265cb67c07768895e5b`。源码位于本机忽略目录 `tmp/modernization/references/FFF_Project`，未安装或执行该项目。

其渲染器明确选择源矩阵／范围，并实现 PQ／HLG 与原色转换。HDR 输出使用 FP16 scRGB、线性 BT.709 原色和 1.0＝80nit 标尺，保留浮点负分量；SDR 输出按源位深选择 8／10bit。这些是具体实现依据，但不足以据此宣布显示色准排名。[3FPlayer 渲染源码](https://github.com/Lake1059/FFF_Project/blob/3fef8eb67d49da6dc92ab265cb67c07768895e5b/FFF.Native/3FP/Render/VideoRenderer.cpp)

它的内核等价测试将基准与优化版本的 GPU 像素回读结果进行比较，值得借鉴。该测试验证优化前后的一致性；不等于独立标准参考或真实屏幕色差测量。[内核等价测试](https://github.com/Lake1059/FFF_Project/blob/3fef8eb67d49da6dc92ab265cb67c07768895e5b/tools/test-kernel-equivalence.ps1)
